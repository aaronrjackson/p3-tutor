Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, where it lives (in the context, in a saved note, or in a manual you search) and why you put it there.

Objective O3: explain context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both jobs come down to one decision you will defend at your design review: what goes into the model's context, what gets saved outside it, and what is looked up only when needed.

Warm-up 2 min

Two questions from the agent loop, to get it back in your head before we build on it.

Recall

The model has just asked for check_calendar("laser cutter", "Friday"). Who actually runs the calendar lookup, and where does its result go next?

Check your answer

The program around the model runs the lookup, not the model. The program then sends the result back to the model as part of its next input and calls the model again. That "next input" is exactly what this lesson is about: what does it contain?

Recall

A student's question needs three tool calls and then a final answer. How many times is the model called?

Check your answer

Four. Every step is a separate model call: one for each tool request, and one for the final answer. Remember this; it is the reason context matters for cost.

The context window 5 min

Start with a concrete case. A student types: "Can I use the laser cutter on acrylic?" Your assistant has to answer using a manual. Before the model writes a single word, the program must hand it everything it needs: the assistant's instructions, the descriptions of its tools, the student's question and, once the model asks for it, the manual text.

Everything the model is given in one call is called its context. Anthropic defines it as "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering for AI agents). A token is the small chunk of text, often a word or part of a word, that the model reads and writes. As a rough rule of thumb, an English word is a bit more than one token.

The context window is the limit on how many tokens the model can work with in one call. The model has no other view of the world: if a fact is not in the context (and was not learned in training), the model cannot use it. This is why a chatbot can state an outdated fact with confidence, which you noticed yourself: its training is old, and nothing newer was put in its context.

The limit counts the text going in and the text coming out together, so an answer needs room too. Window sizes differ between models and change often, so look up your chosen model's current limit instead of memorising one.
A common mix-up

"The model reads my manuals once and then knows them." It is tempting because a chat feels like talking to someone who remembers. But the model's learned knowledge is fixed at training, and your manuals were never part of it. The model "knows" a manual page only while that page's text is in the context of the current call. Once a call ends, the model holds nothing.

Check yourself

Your sponsor adds a new band saw to the makerspace and uploads its manual to a shared folder. The assistant's model was trained a year ago. What must happen for it to answer a band saw question correctly?

Show the answer

The third option. The model can only use what is in its context, so the program has to put the relevant band saw manual text there. Nothing in the folder reaches the model by itself, and retraining is unnecessary.

What is kept between steps 5 min

Now take the agent loop from your last lesson and ask: when the model is called for the second time in a request, how does it know what happened in the first call?

It does not remember. A model call is stateless: the model keeps nothing from one call to the next. What carries the history is the program. At every step it sends the model the whole conversation so far, the original question, each tool request the model made and each result that came back, plus the new result. The model reads that transcript from the top and decides what to do next.

Here is the laser cutter request, step by step. Each row is one model call and shows what is in the context for that call.

CallContext sent to the modelModel outputs
1Instructions, tools, questionRequest: check_calendar
2All of call 1, plus the calendar resultRequest: search_manuals
3All of call 2, plus the manual excerptFinal answer

Two consequences follow, and both matter for your budget.

  • The context grows with every step. Each tool result is appended and stays. Step 3 is bigger than step 2, which is bigger than step 1.
  • You pay for the context again at every step. Model usage is typically billed by tokens, and each call processes the whole context again, so a long request costs far more than the sum of its new text. (Some services discount repeated, unchanged beginnings of a context through caching; check your provider's rules before counting on it.)
A common mix-up

"The model remembers the first call, so I only need to send it the newest result." That would work for a person but not for a model call. If you send only the new result, the model no longer sees the student's question, and it cannot continue the task. The history is the memory, and the program is the one holding it.

Check yourself

In call 2 above, the program forgets to include the student's original question and sends only the calendar result. What is the most likely outcome?

Show the answer

The first option. Each call stands alone, so anything the program leaves out of the context is simply gone for that call.

When the context fills up 5 min

Because the context only grows, a long task eventually hits one of two walls.

The first is the hard limit of the window. The second arrives earlier and is quieter. Anthropic's engineers describe context rot: as the number of tokens in the context grows, the model's ability to accurately recall information from it decreases. They call context "a finite resource with diminishing marginal returns" and say the model has an "attention budget" that every new token uses up (Anthropic). It is a gradual decline rather than a cliff, but it means that putting more in the context is not free, even when it fits. Their guiding rule is to find "the smallest possible set of high-signal tokens" that gets the job done.

So the skill is context engineering: deciding what goes into the context at each call. Three habits cover most of it.

  1. Keep tool results small. A tool that returns one manual section helps; a tool that returns the whole manual wastes the budget. Write tools that return only what the model needs.
  2. Clear what is no longer needed. After the model has used an old tool result, that result can often be dropped. Anthropic calls clearing old tool results "one of the safest lightest touch forms of compaction."
  3. Compact when you must. Compaction means summarizing a conversation that is nearing the limit and starting a fresh context with the summary. The summary should keep decisions and open problems and drop repeated detail. Anthropic's advice is to first tune the summary so that it misses nothing important, and only then trim it.
Compaction is lossy: whatever the summary leaves out is gone from the model's view. If a detail must survive, such as a student's booking time, do not trust it to a summary; write it down somewhere stable, which is the next section.
A common mix-up

"A bigger context window means I can stop choosing what goes in." It is tempting because a bigger window feels like a bigger memory. But a larger window only raises the hard limit. Context rot still applies, and you pay for every token at every step. Choosing what to include stays your job at any window size.

Check yourself

Your assistant has answered ten questions for one student in a single long chat, and answers are starting to miss details that appear early in the chat. Which change fits best?

Show the answer

The third option. Compaction and clearing old tool results shrink the context so the important facts stay easy for the model to find. A bigger window does not fix context rot, and louder instructions do not shrink anything.

Between sessions: notes as memory 6 min

Everything so far lived inside one request or one chat. Now a student closes the app on Monday and returns on Thursday. The assistant has to know that this student passed the laser cutter safety training. What does the model remember?

Nothing. When a session ends, its context is gone, and a new session starts with an empty context. Anything the assistant should "remember" has to be saved by the program outside the model and put back into the context when needed. That saved information is what we call memory in an agent. It is not a feature of the model; it is storage you design.

The simplest form is the one Anthropic describes as structured note-taking, also called agentic memory: the agent writes notes to storage outside the context window and reads them back later. Their examples include a to-do list and a NOTES.md file kept by a coding agent (Anthropic). This tutor works the same way: it keeps a NOTES.md about you, and reads it at the start of each session.

For your assistant, a note could be one small record per student, in a database or a JSON file:

{
  "student_id": "s1042",
  "trained": ["laser cutter", "3D printer"],
  "last_booking": "laser cutter, 2026-11-14 15:00",
  "notes": "prefers afternoon slots"
}

The flow has three moves, and the second one is the one people forget.

  1. Save. When something worth keeping happens (the student books a slot), a tool such as save_note writes it to storage.
  2. Load. When a new session starts, the program, or a tool the model calls such as get_student_record, reads the record and places it in the context.
  3. Use. Only now can the model see "trained on the laser cutter" and skip the training question.

Two design questions come with this, and your team should answer both on purpose.

  • What is worth saving? Facts that stay true and that the assistant cannot easily rebuild: training status, a student's preferences. Not the whole chat transcript, which is large, mostly irrelevant later, and may contain information you do not want to keep.
  • Who decides? Either the program saves fixed fields by rule, which is predictable and cheap, or the model decides what to note, which is flexible but can forget or save something wrong. For something as important as training status, which gates access to dangerous equipment, a rule written by your team, or a check against the official training system, is safer than the model's judgment.
A common mix-up

"The assistant has memory, so it will remember students automatically." That is tempting because chat products often feel like they remember you. In your own agent nothing is remembered unless you build the save step and the load step. If you only build the save step, the model never sees the notes. Both halves are needed.

Check yourself

The team saves each student's training record to a database, but a student reports that the assistant still asks "Have you done the laser cutter training?" at the start of every visit. Which half of memory is most likely missing?

Show the answer

The load step. The records are being saved, so storage works; but a new session starts with an empty context, and unless the program or a tool loads the record, the model cannot know it exists.

Retrieval: finding the right page 5 min

The same idea, saving things outside the context and loading only what is needed, solves your other problem: the manuals. A laser cutter manual may run to many pages, and your assistant has several machines. Putting every manual into every call would cost a lot at every step (remember Figure 2) and would invite context rot. Instead, the manuals live in a store, and the assistant retrieves only the few passages that bear on the question. This is called retrieval.

A common way to find passages is to split each manual into chunks of a few paragraphs and rank them against the question, using either keyword search or a search based on meaning (embeddings). You do not need to build the ranking yourself to design the system; what matters is where retrieval happens. Anthropic describes two styles (Anthropic):

Retrieve up frontRetrieve just in time
HowThe program searches before the model is called and adds the passages to the context.The model gets a search tool, and calls it when it decides it needs a page.
Good forPredictable questions; a fast, simple path.Varied questions; the model can search again with better words.
Watch out forPassages are fetched even if not needed; one search, no second try.Extra steps cost time and tokens; a model with a poor tool can wander.

Anthropic's own example is a hybrid: some files are loaded up front, and others are fetched on demand with search tools. It also suggests a hybrid for content that does not change much, and gives the advice "do the simplest thing that works."

For your assistant, search_manuals(machine, query) is a just-in-time tool. Its result must be short: the top two or three chunks, each labeled with the manual and page, so the model can cite them and the student can check. If the first search misses, the model can search again with different words, which is something up-front retrieval cannot do.

A common mix-up

"With retrieval, the model has read the whole manual." It has seen only the chunks that came back. If the right page was not among them, the model cannot know it exists and may answer from its general training instead, which could be wrong for your machine. That is why chunk quality, ranking and showing the page source matter, and why a "nothing relevant found" result should lead to "I don't know," not a guess.

Check yourself

A student asks, "What speed do I set for cutting 3 mm plywood?" Your assistant retrieves three chunks, none of which mention plywood. What should the instructions tell the model to do?

Show the answer

The third option. Retrying with new words uses the strength of just-in-time retrieval, and admitting a miss is safer than guessing for equipment that can hurt someone.

Worked example and practice 5 min

Worked example

Compare two designs for answering one request, "Is the 3D printer free Friday, and am I trained on it?", using illustrative numbers. The instructions and tool descriptions take 2,000 tokens. A calendar result adds 300. The student record adds 200. The question is small enough to ignore. The assistant makes three calls: calendar, record, then the final answer. Design A pastes the 40,000-token 3D printer manual into the context at the start. Design B retrieves one 1,500-token chunk, but only after the calendar check.

  1. Design A, context per call. Call 1: 2,000 + 40,000 = 42,000. Call 2: 42,000 + 300 = 42,300. Call 3: 42,300 + 200 = 42,500. The manual is in every call because history is re-sent.
  2. Design A, total. 42,000 + 42,300 + 42,500 = 126,800 tokens read across the request.
  3. Design B, context per call. Call 1: 2,000. Call 2: 2,000 + 300 = 2,300. Call 3: 2,300 + 200 = 2,500. No manual chunk is needed for this question, so none is retrieved.
  4. Design B, total. 2,000 + 2,300 + 2,500 = 6,800 tokens, about one-nineteenth of Design A.
  5. Check the quality too. Design A also puts 40,000 tokens of unrelated text next to the facts that matter, which is where context rot hurts. Design B keeps the context small and the useful facts easy to find.

The lesson of the arithmetic: a token in the context is paid for once per call, not once per request. Anything big should enter the context late, only if needed, and leave early.

Your turn

Same setup, but now the student asks, "Is the 3D printer free Friday, and what temperature do I use for PLA?" The call order is: calendar (adds 300 tokens), then search_manuals (adds one 1,500-token chunk), then the final answer. The starting context is 2,000 tokens. Step 1 is given: call 1 reads 2,000 tokens. Work out calls 2 and 3 and the total for the request. Then say which of the three places (context, saved note, searched manual) the PLA temperature came from, and which place the student's training status would come from.

Show a solution

Call 2 reads 2,000 + 300 = 2,300 tokens. Call 3 reads 2,300 + 1,500 = 3,800 tokens. The total is 2,000 + 2,300 + 3,800 = 8,100 tokens. The PLA temperature came from the searched manual, retrieved just in time and appended to the context for call 3. The training status would come from the saved note (the student record), loaded into the context when the session starts or through a record tool.

Summary 2 min

  • The context is all the text the model gets in one call, and the context window is the limit on it. The model can only use what is in it.
  • Between steps, the program keeps the history and re-sends all of it each call. The context grows, and you pay for it each call. Past a point, bigger also means less accurate (context rot).
  • Between sessions, nothing survives unless you save notes outside the model and load them back. Memory is storage you design.
  • Retrieval keeps big sources, like manuals, out of the context until a few relevant chunks are needed, either up front or just in time.
