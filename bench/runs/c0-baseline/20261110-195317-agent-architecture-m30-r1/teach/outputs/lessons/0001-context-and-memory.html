Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes in the model's context at each step, what gets saved between visits, and how it finds the right page in a long manual.

Warm-up 2 min

Recall

A student asks, "Is the laser cutter free on Friday?" Without looking back: in the agent loop, who actually runs the check_calendar tool, the model or the program around it? And what happens to the result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then sends the result back to the model as part of its next input and calls the model again.

That last sentence is today's topic. "Part of its next input" raises a question: what exactly is the model shown each time it is called, and for how long does anything last?

The context window: what the model sees 5 min

Start with a concrete case. Priya opens the makerspace assistant and types: "What speed should I run the bandsaw at for 3 mm acrylic?" Before the model writes a single word, the program has put together one big block of text to send. It holds, in order:

  • the system prompt, your standing instructions ("You are the makerspace assistant. Only answer from the manuals. Ask before booking.");
  • the tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and the rest;
  • the conversation so far: Priya's question, and later any tool requests and results.

All of that text, plus the answer the model is writing, makes up the context window: "all the text a language model can reference when generating a response, including the response itself" (Claude API docs, context windows). The docs compare it to the model's working memory. The model has nothing else to look at.

The window is measured in tokens, the small chunks of text a model reads and writes; a token is roughly a short word or part of a longer one. Two things follow, and you will use both all lesson:

  1. There is a limit. Go over it and the request fails, or the model stops early (same docs page).
  2. Every token costs money on every call, whether it is your instructions, a tool result or a pasted manual. Your sponsor's budget is spent in tokens.
A common mix-up

"The model remembers me." It is tempting, because chatbots feel like they do. But the model itself keeps nothing between calls: each call starts fresh from the text it is handed. Within a conversation, the program re-sends the earlier messages every time; the docs say that in API requests "previous turns are preserved completely" and accumulate with each turn (context windows). Memory is something your program builds, not something the model has.

Check yourself

Priya's session is running. Which of these is not inside the context window the model sees on its next call?

Show the answer

The booking database. The model only sees text the program puts into the window; the database is reachable only through a tool, and only the result of a tool call enters the context.

Between steps: the context grows 5 min

Now put this together with the loop from last time. Each step of the agent loop is a separate model call, and the model remembers nothing between calls. So how does it "know" what happened at step 1 when it is at step 3? Because the program appends each tool request and each result to the conversation and sends the whole thing again.

Anthropic's engineering team describes the agent's job as curating this: an agent running in a loop keeps producing information that "could be relevant for the next turn of inference," and that information must be "cyclically refined" (Effective context engineering for AI agents). This work is called context engineering: deciding which tokens are in the window at each call.

This is the reason cost surprises people. You pay for the whole window on every call, so a long loop costs far more than the sum of what the tools returned. A big tool result, such as a pasted manual page, is paid for again at every later step. (Prompt caching can make repeated tokens cheaper, but the docs are clear it changes the price, not whether they count toward the window: context windows.)

The model's own previous requests are in the window too, though they are short. In the arithmetic below we count them at 100 tokens each.
Check yourself

At step 6 of a long run, the assistant wants to use something it learned from the tool result at step 2. What makes that possible?

Show the answer

The program re-sent it. Anything the model "remembers" within a run is text that is still in the window.

When the window fills up 5 min

You might think the fix is simply a model with a bigger window. It helps with the hard limit, but there are two other problems.

First, cost: a bigger window you fill is a bigger bill on every call. Second, quality. The docs name context rot: "As token count grows, accuracy and recall degrade" (context windows). Anthropic's engineering post calls this a gradient, not a hard cliff, and says each new token uses up some of the model's limited "attention budget" (Anthropic engineering). Research agrees in a specific way: in "Lost in the Middle" (Liu et al., published in TACL 2024), models answered best when the relevant passage was at the start or end of a long input and worse when it was in the middle.

So the goal Anthropic states is the smallest set of high-signal tokens that gets the job done, not the biggest window you can afford.

A common mix-up

"If the window is big enough for the whole manual, just paste the manual into every request." Tempting because it is simple, and it does work for a tiny manual. But you pay for every token on every call, and the manual sits between the model and the one paragraph it needs. A 50-page manual pasted in is paid for at each of the four calls in a single request; you will count it in the worked example.

When a long run really does outgrow the window, there are two standard repairs, both described in the Anthropic post:

  • Clearing old tool results: drop results the model no longer needs, leaving a placeholder. The post calls this "one of the safest lightest touch forms of compaction."
  • Compaction: have the model summarize the conversation so far, then start a fresh window holding the summary. In Claude Code the summary keeps decisions, unresolved bugs and details and drops redundant tool output.

Both lose information, so the post's advice is to first make the summary catch everything important, then trim it down.

Check yourself

Your assistant's runs are short: three or four steps. A teammate proposes adding compaction. What is the most sensible reply?

Show the answer

Not yet. Compaction is a repair for runs that outgrow the window. For short runs the cheaper lever is keeping each tool result small.

Between sessions: notes as memory 6 min

Everything so far disappears when the session ends: the next time Priya opens the assistant, the program starts a new, empty window. Yet the assistant must know she finished laser cutter training last month.

The answer is external memory: information the program saves outside the window, in a file or database, and loads back in when needed. Anthropic's name for the pattern is structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window" and pulls them back later; their examples are a to-do list and a NOTES.md file (Anthropic engineering).

For your assistant, a note might look like this, one file per student:

students/priya.md
- Completed: laser cutter safety training (2026-10-03)
- Not yet trained: bandsaw, 3D printer
- Preference: books evenings only

Anthropic's API even ships this as a ready-made memory tool. It runs client-side: "Claude requests file operations, and your application runs them," so you choose where files live (Memory tool docs). Notice it is the same pattern as last lesson: the model asks, your program acts. The commands are file operations such as view, create, and str_replace. The model decides what to write down; you decide where it goes and what is safe to store.

What is worth saving?

Keep in context (this run)Save as a note (every run)
Today's question and the steps takenTraining completed, and the date
Raw calendar resultsStable preferences the student stated
The manual page just retrievedNothing: the manual stays in the manual store

The rule of thumb: save short facts that will still be true next visit and cannot be looked up cheaply. Do not copy what a tool can re-fetch. Note also that a training record is something the school's system should own; a note is a convenience copy, so check with your team which source wins if they disagree.

Check yourself

On Monday Priya tells the assistant she is left-handed and prefers booking after 5 pm. On Thursday she opens a new session. What must be true for the assistant to use this?

Show the answer

A note was saved on Monday and loaded on Thursday. Window size does not matter here: a new session starts empty.

Retrieval: finding the right page in a long manual 5 min

The manuals are too long to paste in (see the cost above) and too long to save as notes. The third kind of memory is retrieval: keep the manuals in a store outside the window, and bring in only the few passages relevant to the current question.

Anthropic's post describes two timings, and this choice is yours as the designer:

  • Up front: before the model is called, the program searches (for example with embeddings, which match by meaning) and puts the top passages in the context.
  • Just in time: the agent holds only lightweight identifiers, such as file paths or stored queries, and loads data with tools when it needs it. Claude Code works this way for files, using search tools such as grep and glob, while loading its CLAUDE.md file up front. The post's trade-off: just-in-time is more flexible but slower, and needs good heuristics; its advice is that "do the simplest thing that works" will likely stay the best guidance (Anthropic engineering).

For your assistant, search_manuals(machine, question) is just-in-time retrieval: a tool, so the agent loop already supports it. Its result is the part to design carefully. Return three passages with the machine name and page number, not forty pages. Each result enters the window and is re-paid at every later call, and the page number lets the assistant cite where an answer came from.

Check yourself

Priya asks about bandsaw speed for acrylic. Which design is the best fit for a small budget?

Show the answer

Search and return a few passages. It keeps the window small and the cost low, and each passage can be cited.

Worked example and practice 8 min

Worked example

The assistant gets the question: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Fixed part (system prompt plus tool descriptions): 2,000 tokens. The question: 50 tokens. The run has four model calls. Each tool request is 100 tokens; results are: calendar 400, manual passages 1,500, training record 200. How many input tokens are sent in total across the four calls?

  1. Call 1 sees the fixed part and the question: 2,000 + 50 = 2,050.
  2. Call 2 adds request 1 and the calendar result: 2,050 + 100 + 400 = 2,550.
  3. Call 3 adds request 2 and the manual passages: 2,550 + 100 + 1,500 = 4,150.
  4. Call 4 adds request 3 and the record: 4,150 + 100 + 200 = 4,450.
  5. Total: 2,050 + 2,550 + 4,150 + 4,450 = 13,200 input tokens. Only 2,100 tokens of results were fetched (400 + 1,500 + 200), yet 13,200 were sent, because each result is re-sent with every later call. The 1,500-token manual passage arrives with call 3's input, so it is carried by calls 3 and 4.

Now compare with pasting a 50,000-token manual into the fixed part. Every call carries it: 4 × 50,000 = 200,000 extra tokens, for a total of 213,200. That is about 16 times the retrieval design, for the same answer.

Your turn

A new request: fixed part 2,000 tokens, question 100 tokens, three model calls. After call 1 the model requests a tool (100 tokens) whose result is 300 tokens; after call 2 it requests another (100 tokens) whose result is 1,200 tokens; call 3 writes the answer. Call 1 is done for you: 2,100. Work out calls 2 and 3 and the total input tokens.

Show a solution

Call 2: 2,100 + 100 + 300 = 2,500. Call 3: 2,500 + 100 + 1,200 = 3,800. Total: 2,100 + 2,500 + 3,800 = 8,400 input tokens. The 1,200-token result is the biggest item, and it is carried only by the last call; a result that arrives early is carried by more calls, so large results arriving early cost the most.

Design prompt

Sketch, in three lines, for your assistant: (1) what lives in the fixed part, (2) what you save as notes per student, (3) what search_manuals returns. Then look at the table in the notes section and ask: could any line be cheaper?

Summary 2 min

  • The model sees only its context window: system prompt, tool descriptions, conversation and answer. It keeps nothing between calls.
  • Within a run, the program re-sends everything each step, so cost grows with every result you keep.
  • Big windows still cost money and suffer context rot; aim for the smallest set of useful tokens, with clearing or compaction when runs get long.
  • Between sessions, memory is notes your program saves and reloads; between a question and a long manual, it is retrieval.

Say it in your own words: explain to a teammate why the assistant forgets Priya on Thursday unless you build something, and name the two things you would build.
