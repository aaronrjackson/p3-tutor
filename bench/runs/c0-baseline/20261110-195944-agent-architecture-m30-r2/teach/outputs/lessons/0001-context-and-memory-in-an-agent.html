Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in a saved note, or in a searchable library, and say why.

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small budget. All three come down to one design question: what does the model see at each step? You will defend your answer at the design review.

Warm-up 2 min

Recall

Without looking back: in the agent loop, the model asks for a tool. Who runs the tool, and where does the result go next?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That "next input" is exactly what this lesson is about: what goes into it, and what gets left out.

The context window 5 min

Start with a concrete case. A student types: "Can I use the laser cutter on acrylic?" Before the model writes a word, the program assembles a block of text: the assistant's instructions, the descriptions of its tools, and the student's question. The model reads that block and writes a reply. The block is the model's entire view of the world for that call.

That block is the context: all the text the model is given for one call. The context window is the most the model can take in one call, counted in tokens, the small chunks of text (a short word, or part of a longer one) that models read and write. The limit covers the input and the model's output together (Designveloper, a secondary explainer; check your model provider's documentation for the exact limit of the model you choose).

Three things follow, and they are the heart of this lesson.

  1. The model only knows what is in the context (plus what it learned in training, which may be out of date, as you have noticed with chatbots). If the laser cutter's acrylic rule is not in the context, the model will guess.
  2. The window is finite. A 200-page manual may not fit, and even when it fits, there are other costs.
  3. You pay for what you send. Model providers usually charge per token, for input and for output. A bigger context costs more on every call.

The third option. With no manual in the context, the model uses what it learned in training, which may not match your machine.

What is kept between steps 6 min

Now the surprising part. The model itself keeps nothing between calls. Each call starts fresh: the model reads the context you hand it and writes a reply, and then it is done. Anything it should "remember" at the next step must be put into the next context by your program.

In the agent loop, that is exactly what the program does. After each step it appends the model's tool request and the tool's result to a running list of messages, and it sends the whole list again. The history is that list. Anthropic's engineering team describes agents as running in a loop whose context keeps growing, with each turn of the loop producing more data that could be relevant for the next one (Effective context engineering for AI agents).

A common mix-up

"The model remembers what happened earlier in the task." It feels true because the replies stay on topic. But the model is re-reading the history your program re-sent. If your program forgot to include the calendar result, the model would have no idea it had ever asked. The same goes between conversations: a new conversation starts with an empty history unless you load something into it.

This explains cost. Suppose the setup (instructions and tool descriptions) is 1,500 tokens, the question is 50, and each tool result adds 1,000. Count the input tokens the model reads across a four-call run (three tools, then the final answer):

Worked example: input tokens in a run
  1. Call 1 reads setup plus question: 1,500 + 50 = 1,550. (It also writes a short tool request, which we ignore here.)
  2. Call 2 re-reads all of that plus result 1: 1,550 + 1,000 = 2,550.
  3. Call 3 adds result 2: 3,550.
  4. Call 4 adds result 3: 4,550.
  5. Total input read: 1,550 + 2,550 + 3,550 + 4,550 = 12,200 tokens, although only 4,550 tokens of unique text exist.

So long runs cost much more than the sum of their parts: each extra step re-pays for everything before it. That is why the step limit from your first quiz matters for the budget as well as for safety. (Some providers discount text that is repeated exactly at the start of each call, called prompt caching. It helps, but it does not remove the growth.)

When the window fills up 5 min

A growing history hits two limits. The hard one: it can exceed the window, and then the call fails or something must be dropped. The soft one: even before that, more text is not always better. Research on long inputs found that models do best when the relevant fact sits at the beginning or end of the context, and worse when it is buried in the middle (Liu et al., "Lost in the Middle"). Anthropic's guide therefore treats context as a limited resource and aims for the smallest set of high-signal tokens that gets the job done (Anthropic).

So your program has three simple tools for keeping the context useful:

TechniqueWhat it doesCost
TrimmingDrops the oldest or least useful messages, such as a bulky tool result already used.Details may be lost for good.
CompactionAsks the model to summarise the history, then restarts with the summary in place of the full text.One extra model call; the summary can miss a detail.
Lean tool resultsTools return only what the model needs, such as three booking slots rather than a whole month.Needs careful tool design.

The same guide lists summarising history when it nears the limit, and keeping notes outside the window, as the standard ways to keep long tasks going (Anthropic). For your assistant, the cheapest of the three is usually the third: design the tools so they never return junk.

A common mix-up

"A bigger context window solves everything." It is tempting: just paste the whole manual in. But you pay for every token on every call, and the model may use a long context less well, as the research above shows. A bigger window raises the ceiling; it does not make filling it a good idea.

Between sessions: notes as memory 5 min

Everything so far lives inside one run. When the run ends and the program exits, the context is gone. A student who finished laser cutter training on Monday will come back on Friday to a brand-new, empty context. If the assistant must know "Priya passed laser training", something has to carry that across.

The answer is plain: memory in an agent means information stored outside the model, usually in a file or a database, that the program loads into the context when it is useful. The model does not "learn" Priya's status; your program writes it down, and later reads it back. Anthropic's guide calls this structured note-taking: the agent writes notes to storage outside the context window, and pulls them back in at later times (Anthropic).

You already know enough Python to see the shape. A note store can be a JSON file:

{"priya": {"trained": ["laser cutter"], "updated": "2026-11-02"}}

Two tools make it work: save_note(student, text) and read_notes(student). At the start of a session, the program (or the model, via read_notes) loads Priya's entry into the context. During the session, when she completes training on the 3D printer, the model calls save_note.

A common mix-up

"A chatbot product that remembers me must have a model that learns." Not in the way it feels. Such products typically work as above: saved notes are put back into the context. (Quiz 0001 had an option that assumed automatic memory of earlier conversations; this is why it was wrong.)

Notes bring design choices that matter for your review: what to save (facts that stay true and change decisions, like training status; not whole chat logs), who may write (a model that can write notes can also write a wrong one, so training status is safer if only the staff system sets it), and how to keep it small (load only the current student's entry, so notes do not bloat every context).

Retrieval from a long manual 5 min

Notes are for small facts about people. The manuals are different: long, fixed, and mostly irrelevant to any one question. A student asking about acrylic needs one paragraph of the laser cutter manual, not the other 199 pages. Retrieval means searching a collection and putting only the best-matching pieces into the context.

The usual recipe has four steps, done ahead of time and then at question time:

  1. Split each manual into chunks: short passages of a few paragraphs, ideally with the machine and section name attached.
  2. Index them so they can be searched. Simple keyword search works for part names and settings; embeddings (numbers that capture meaning, so "cut" and "slice" land close together) help when students use different words than the manual.
  3. Search when a question arrives, and take the top few chunks.
  4. Add those chunks to the context, with their source, and let the model answer from them.

In an agent, step 3 is usually just another tool, like the search_manuals tool in your quiz. The model decides when to call it and what to search for. Anthropic describes this as "just-in-time" retrieval: the agent keeps light references, such as file names or queries, and loads data into context only when needed, rather than loading everything up front (Anthropic).

Retrieval can fail in two ways, and both are worth naming at your review. It can miss: the right chunk was not in the top few, because it was split badly or the student used unusual words. Or it can mislead: a chunk about a different machine looked similar, and the model answered with it. The defences are plain: attach the machine name to every chunk, return a few chunks and not one, and make the assistant say which manual and section it used, so a student can check.

Worked example and practice 5 min

Worked example: the request "Can I use the 3D printer tomorrow at 2 pm?"

Decide where each piece of information lives.

  1. Assistant rules and tool descriptions: short, needed on every call. They go in the context, at the start, every time.
  2. The student's training status: small, durable, about one person. It goes in a note, and the program loads that student's entry at the start of the session.
  3. The 3D printer's rules for new users: long and fixed. They go in the manual library, and the model retrieves the matching chunk only if the question needs it.
  4. Tomorrow's slots: live and short-lived. The tool fetches them when asked, returning one day, and the result stays in history only as long as it is useful.
  5. Check: nothing long is sent on every call except the rules, which keeps cost per request low.
Your turn

Now the request: "I finished the vinyl cutter safety quiz; can I book it Thursday, and what blade should I use for thick vinyl?" The first step is done for you: the assistant rules and tool descriptions go in the context. Place the other four items, giving a reason for each: (a) the fact that the student finished the quiz, (b) the blade guidance, (c) Thursday's slots, (d) the chat so far when the student returns next week.

Show a solution

(a) The quiz result is a durable fact about one person: save a note, ideally written by the staff system or after the assistant confirms it. (b) The blade guidance is in the long manual: retrieve the matching chunk and cite it. (c) Thursday's slots are live data: a calendar tool call returning only that day. (d) The chat is not kept by default. Next week the context starts empty, and only the saved note carries over; save a short summary only if it will change a future decision.

Summary 2 min

  • The model sees only the context of the current call; it keeps nothing between calls.
  • Between steps, the program re-sends the growing history. That costs more with every step, and long contexts can be used less well.
  • Between sessions, memory is notes the program saves and loads back, not learning inside the model.
  • Long manuals live outside the window; retrieval brings in only the best-matching chunks.
