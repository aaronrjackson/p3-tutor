Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a manual you search on demand.

The program around the model runs the tool, not the model. The model only writes a request naming the tool and its arguments. The program puts the result back in front of the model, and the model is called again. Today's question: what exactly does the model see on that next call, and what happens when the conversation ends?

The context window 5 min

Start with an example. A student asks your assistant: “Is the laser cutter free Friday?” Your program sends the model a block of text. Part of it is your instructions (“You are the makerspace assistant. Be brief.”). Part is the descriptions of your tools. Part is the student's question. The model writes a reply from that block of text and nothing else.

That block is the context: the set of tokens given to the model when it writes. Anthropic's engineering team defines it in nearly these words in Effective context engineering for AI agents. A token is a small chunk of text, often a short word or part of a word. The context window is the most tokens the model can take in one call, with its own reply counted against the same limit.

Everything the model can use at that moment must be inside the window. It cannot look at your booking system, your manuals or yesterday's chat unless text from them has been put in the window.

A common mix-up

“The model remembers what we talked about, like a person does.” It feels that way in a chat app, but the model itself keeps nothing between calls. The program resends the earlier messages every time. If the program stops resending them, the model has no idea they happened. The model is the same at the start and the end of a chat; only the text you send it differs.

What is kept between steps 5 min

Now put this together with the loop from last time. Inside one request, every step is a separate model call, and each call gets the whole context so far: instructions, tool descriptions, the question, and every tool request and result since. Nothing is kept except what the program appends and resends.

That has a cost consequence. You pay for the tokens you send on every call, so a step's tool result is paid for again on every later step. Long tool results are expensive.

Providers can offer cheaper rates when the start of the context repeats exactly from call to call. Check your provider's pricing before relying on this; this lesson does not use it.

Why bigger is not free 4 min

If the window is big, why not put everything in? Two reasons: cost, as above, and quality. Anthropic's post describes context rot: as the number of tokens grows, the model's ability to recall information from the context gets worse. It describes this as a gradual slope, not a cliff, and says it affects all models to some degree. It frames context as an attention budget: each new token uses some of the model's limited ability to focus. The goal it sets is “the smallest possible set of high-signal tokens” that gets the result you want (Anthropic Engineering).

An everyday comparison: you can fit twelve textbooks into a backpack, but you will not find the one formula faster. A desk with just the page you need is better.

A common mix-up

“A bigger context window means I do not have to decide what to include.” Tempting, because it removes work. But a stuffed window costs more on every call and buries the useful lines among useless ones. Window size is a limit, not a goal.

What is kept between sessions 5 min

A session is one conversation from start to finish. When it ends, the context is gone. Next Tuesday, the same student starts a new session with an empty window. By default the assistant does not know their name, that they finished the laser cutter safety course, or what they booked last week.

Anything that must survive has to be written down outside the model, then put back into the window later. That is what people mean by memory in an agent: storage that your program keeps, plus a way to read it back into the context. Anthropic's post calls the agent-managed version structured note-taking: the agent writes notes to storage outside the context window and reads them back when needed. Its examples are a to-do list in Claude Code and an agent that keeps a NOTES.md file. In the post's Pokémon example, an agent keeps maps, achievements and strategy notes, and after its context is reset it reads those notes and continues (Anthropic Engineering).

For your assistant, this could be a very small thing. A record per student in a JSON file or database:

{"student_id": "s1042",
 "trained_on": ["laser_cutter", "3d_printer"],
 "last_booking": "2026-11-03 laser_cutter"}

Two tools, get_student_record(student_id) and save_note(student_id, text), are enough. You described the shape of tools in the last lesson; memory is just two more tools whose storage lives outside the model. Notice the choice you are making: facts that the system must get right, like training status, should be written by your program from the real training database, not by the model's guess about what it should remember. The model-written notes are for softer things, like “prefers morning slots.”

Tool vendors now offer ready-made file-based memory tools, and agent libraries describe the same pattern, for example the AI SDK's page on agent memory. In each, your program does the actual reading and writing; the model only asks.
A common mix-up

“A bigger window means the assistant can remember students between visits.” A window is only the text in one call. However large, it is empty when a new session starts. Memory across sessions needs storage outside the window.

Retrieval: finding the right page 5 min

The manuals are the other memory problem. A laser cutter manual may run to hundreds of pages. Pasting every manual into every call would be costly and, as we saw, would hurt quality. Retrieval means fetching only the part you need and placing it in the context for this call.

Anthropic's post contrasts two ways to do it:

  • Up front. Before the model runs, your program searches the manuals (often with an embedding, a list of numbers that places text with a similar meaning close together) and puts the best matches in the window.
  • Just in time. The model gets lightweight pointers, like page titles or file names, and a tool such as search_manuals(machine, query). It fetches what it needs, when it needs it. The post says this lets the agent explore step by step, at the price of being slower and needing good tools (Anthropic Engineering).

The post also notes that a mix is common: some things loaded up front, the rest fetched on demand, and it advises “do the simplest thing that works.”

Here is a concrete case. A student asks, “What is the maximum material thickness for the laser cutter?” With just-in-time retrieval, the model writes a request like search_manuals("laser cutter", "maximum material thickness"). Your program searches, returns two or three matching paragraphs (a few hundred tokens), and the model answers from those paragraphs. If the search returns nothing useful, the model can try different words, which is one reason this approach suits an agent. Because the answer comes from a page the model has just read, you can also have it name the page, so the student can check it. That matters for safety questions about machines.

Two practical rules follow. First, return small pieces, a page or a section, never a whole manual, since everything returned is paid for on every later call. Second, write the tool description so the model knows what the store holds: “Searches the machine manuals. Use for how-to, settings and safety questions. Not for bookings.”

When one task outgrows the window 3 min

Sometimes a single long task fills the window, for example a staff member rebuilding the whole month's schedule with dozens of tool calls. The post names three tools for this (Anthropic Engineering):

  • Compaction: ask the model to summarize the context when it nears the limit, then start a fresh window with that summary. The summary keeps decisions and open problems and drops redundant tool output.
  • Notes: as above, write progress to storage and read it after a reset.
  • Sub-agents: a helper explores in its own clean window and returns only a short summary. The post says that summary is often 1,000 to 2,000 tokens. You will meet this properly when we reach multi-agent systems.

For your first design review you probably need none of them: a student question is short. Know they exist, and use them only if requests actually run long.

Worked example and practice 5 min

Worked example

The system prompt and tool descriptions take 2,500 tokens, and the student's question is 50 tokens. The assistant needs three tool calls. Each tool request the model writes is 50 tokens. Results: calendar 200, manual page 3,000, training record 100. How many input tokens do you pay for across the four model calls? (Numbers are invented for the exercise.)

  1. Call 1 sends instructions, tools and question: 2,500 + 50 = 2,550.
  2. Call 2 adds the model's request (50) and the calendar result (200): 2,550 + 250 = 2,800.
  3. Call 3 adds another request (50) and the manual page (3,000): 2,800 + 3,050 = 5,850.
  4. Call 4 adds a request (50) and the record (100): 5,850 + 150 = 6,000.
  5. Total: 2,550 + 2,800 + 5,850 + 6,000 = 17,200 input tokens. The 3,000-token page, sent once by the tool, was paid for twice.
Your turn

Same request, but the manual search returns the whole 12,000-token manual instead of one page. Step 1 is done for you: calls 1 and 2 are unchanged, at 2,550 and 2,800 tokens. Work out calls 3 and 4 and the total. Then say how many more tokens the bigger result adds to the total, compared with 17,200.

Show a solution

Call 3: 2,800 + 50 + 12,000 = 14,850. Call 4: 14,850 + 50 + 100 = 15,000. Total: 2,550 + 2,800 + 14,850 + 15,000 = 35,200 input tokens, so 18,000 more than the 17,200. The extra 9,000 tokens in the result were paid for twice, which is where the extra 18,000 comes from. Retrieving the right page saves money and keeps the window cleaner.

Summary 2 min

  • The model sees only the context window. It keeps nothing between calls; your program resends what it chooses.
  • Within one request, every step resends the whole context, so long tool results are paid for again on every later call, and a fuller window recalls less well.
  • Between sessions, only what you store outside the model survives: records and notes read back by tools.
  • Retrieval puts just the needed manual page in the window, up front or just in time.
