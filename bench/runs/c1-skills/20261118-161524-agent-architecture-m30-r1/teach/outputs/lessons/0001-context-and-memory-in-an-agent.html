Context and memory in an agent

By the end of this lesson you can decide what your makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status. It must also stay inside a small model budget. All three jobs depend on one thing: what the model sees at each step.

Warm-up 2 min

The program around the model runs the tool. The program then sends the result back to the model as part of its next input, and calls the model again. This lesson looks at that "next input": what is in it, and how big it gets.

Recall

A model writes text one token at a time. What is a token, in your own words?

Check your answer

A token is a small piece of text, often a word or part of a word. Models read and write tokens. You will see that tokens are also what the context window limits, and what you pay for.

The context window 6 min

Motivation. A model has no view of your booking system, your manuals or your students. It sees only the text you send it. If a fact is not in that text, the model cannot use it. So the first design question is always: what text goes in?

Definition. Context is the set of tokens included when the model is called (Anthropic Engineering). The context window is the maximum number of tokens the model can handle in one call. Everything counts toward it: the system prompt, every message, the tool results, the tool definitions, and the model's own output (Claude docs).

Example. A student asks, "How do I change the blade on the band saw?" The assistant sends the model the system prompt (about 300 tokens), three tool definitions (about 600 tokens) and the question (about 20 tokens). That is about 920 tokens in. The model replies with a request to call search_manuals. The numbers here are made up to show the idea; real counts depend on the text.

Nuances

  1. Nuance 1: The window is for input and output together. A long reply uses room that the input could have used.
  2. Nuance 2: Size differs by model. Current models range from about 200,000 to 1,000,000 tokens. Check the documentation for the model you pick. A big window does not mean a good idea to fill it.
  3. Nuance 3: Tool definitions count. Twenty tools with long descriptions can use thousands of tokens on every call, before the student asks anything.
  4. Nuance 4: Over the limit means an error. If the input alone is too long, the API refuses the request.
Check yourself

Your assistant has a 1,500-token system prompt and four long tool definitions. A student has typed nothing yet. Is the context empty?

Show the answer

The third option. The system prompt and tool definitions are part of every call. The first option ignores them. The second option invents a memory that does not exist.

What is kept between steps 7 min

Motivation. The agent loop calls the model many times for one request. You need to know what the model carries from one call to the next. The answer surprises many people: nothing.

Explanation. The model keeps no state between calls. The API is stateless: each request must carry the history, and each turn's input is all the earlier conversation plus the new message (Claude docs). So your program keeps a list of messages. After each step, it adds the model's output and the tool result to the list. Then it sends the whole list again. This is how the model "remembers" step 1 at step 4.

Example. The assistant answers: "Is the laser cutter free Friday, and do I need training?" Say the question, system prompt and tool definitions are 1,000 tokens. A calendar result adds 200. A manual search result adds 3,000. A training-record result adds 100.

CallInput tokens
1: question1,000
2: plus calendar1,200
3: plus manual search4,200
4: plus training record4,300
Total input paid10,700

The final context is only 4,300 tokens. But the request used 10,700 input tokens. Every extra step re-sends the large manual result. That is why long loops cost money. (Prompt caching can make re-sent text cheaper; it does not make it free, and the text still fills the window.)

Nuances

  1. Nuance 1: Bigger results cost at every later step. A 3,000-token result in step 3 is paid for again in step 4, step 5 and so on. Return short results from your tools.
  2. Nuance 2: More context is not always better. As the token count grows, the model's recall of the content drops. Anthropic calls this context rot, and treats context as a finite resource with diminishing returns (Anthropic Engineering). The aim is the smallest set of high-signal tokens that gets the job done.
  3. Nuance 3: You can shrink the history. Compaction summarizes a long conversation and starts a new window with the summary. A lighter method is tool-result clearing: remove old tool outputs that the agent can fetch again.
  4. Nuance 4: Compaction can lose facts. A summary can drop a detail that matters later. Keep the facts you must not lose, such as the booking time the student agreed to.
A common mix-up

"A bigger context window means I do not need to manage context." This is tempting because a big window can hold a whole textbook. But the window is not the only limit. Every token is paid for at each step, and recall gets worse as the context grows. A 40-step run with a big window still costs a lot and can still get confused.

Check yourself

Step 3 of a run adds a 5,000-token manual result. The run takes 3 more steps after that. About how many input tokens does that one result add over the whole run?

Show the answer

The third option. The result is first sent in the call right after step 3. It is then re-sent in the 3 later calls. That is 4 calls with 5,000 tokens each, so 20,000 tokens.

What is kept between sessions 7 min

Motivation. A student trains on the laser cutter on Monday. On Thursday they return and ask to book it. Your assistant must know they trained. If it does not, it will ask them again, or worse, allow an untrained student on the machine.

Explanation. If the model keeps nothing between calls, it keeps even less between sessions. When a session ends, the message list is gone, unless your program saves it. A new session starts with an empty list. So any fact that must survive has to be written to storage outside the context window, and read back in when needed. Anthropic calls one form of this structured note-taking: the agent writes notes to persistent memory and reads them later. Examples are a to-do list or a NOTES.md file (Anthropic Engineering).

Example. Your assistant has two tools: save_note(student_id, text) and read_notes(student_id). On Monday, a staff member records that Sam finished laser cutter training. The program runs save_note("sam", "laser cutter training done, May 6") into a database. On Thursday, Sam logs in. The program calls read_notes("sam") before the first model call and puts the result in the context. Now the model can say, "You trained on the laser cutter on May 6. Which day do you want to book?"

A real tool exists for this. Anthropic's memory tool lets the model create, read, update and delete files. It is a client-side tool: the model asks, and your program does the storage work (Claude docs, memory tool). The model never touches the disk itself. This is the same rule as in the agent loop.

Nuances

  1. Nuance 1: Facts like training status should not depend on the model's notes. A staff record in your database is more reliable than a note the model wrote. Let the program load such records in directly.
  2. Nuance 2: Notes must be short and be read selectively. If you load every note about every student, you fill the window again. Load only the notes for this student.
  3. Nuance 3: Notes can be wrong or stale. A training can expire. Store a date, and have the assistant check it.
  4. Nuance 4: Private data needs care. A student's notes must load only for that student. Your program must enforce this; a prompt that says "do not show others' notes" is not enough.
A common mix-up

"The assistant remembers earlier chats on its own." This is tempting because chat apps seem to remember you. But in an agent you build, the model starts each call with only what you send. Chat apps that remember do it with the same method: the app saves things and puts them back in. Your assistant has no memory until you build it.

Check yourself

Your assistant should recall that a student prefers morning bookings. Where should that fact live?

Show the answer

The second option. Only storage outside the context survives between sessions, and loading it per student keeps the context small and private.

Retrieval: finding the right page 7 min

Motivation. A laser cutter manual may have 200 pages. A student asks, "What does error E-14 mean?" You cannot put every manual in every call: it costs too much, and it makes recall worse. You need to find the right page and put only that in.

Definition. Retrieval means searching a store for the pieces that match the question, and adding only those pieces to the context. A common design is called RAG (retrieval-augmented generation). Its steps (Anthropic, Contextual Retrieval):

  1. Split each manual into chunks of a few hundred tokens.
  2. Turn each chunk into an embedding: a list of numbers that captures its meaning, so similar meanings get similar numbers. Store them.
  3. At question time, embed the question, find the closest chunks, and add the top few to the context.

Embeddings find meaning but can miss exact strings. BM25 is a keyword ranking method that is good with unique identifiers and technical terms. Anthropic's example is an error code such as "TS-999", which an embedding search may miss and keyword search finds. Using both together, called hybrid search, is a standard fix (Anthropic). For your manuals, this matters: error codes and part numbers are exact strings.

Example. A student asks, "What does E-14 mean on the laser cutter?" Embedding search returns chunks about the laser's error messages in general. Keyword search finds the one chunk that contains the string "E-14": "E-14: water flow too low. Check the chiller before restarting." Hybrid search ranks that chunk first. The program adds it to the context, and the model answers in one step with a source.

Nuances

  1. Nuance 1: A chunk can lose its context. A chunk that says "Set it to 40 mm/s" does not say which machine. Anthropic's fix, contextual retrieval, adds a short note to each chunk before indexing, such as "From the band saw manual, cutting speed section." Its tests cut missed retrievals from 5.7% to 1.9% when it was combined with keyword search and reranking, in its own experiments in 2024 (Anthropic). A simple version for you: put the machine name in every chunk.
  2. Nuance 2: Maybe you do not need retrieval. Anthropic says that if the knowledge base is under about 200,000 tokens (about 500 pages), you can put it all in the prompt, and prompt caching makes this faster and cheaper (Anthropic). But recall gets worse as context grows, and you pay for caching too. Test both on real questions.
  3. Nuance 3: Retrieval can happen up front or on demand. Up front, the program searches before the model runs. On demand ("just in time"), the model gets a search_manuals tool and decides when to search. On demand is slower but flexible, and agents can waste context if the tool is poor (Anthropic Engineering). Many designs use both.
  4. Nuance 4: Retrieval does not teach the model. The chunk is in the context for this call only. In the next session, the model knows nothing about it unless the program searches again.
Check yourself

A student asks about "part no. 7731-B" on the 3D printer. Which search finds the exact part number most reliably?

Show the answer

The third option. Keyword search such as BM25 is strong on unique identifiers. Embeddings are strong on meaning. A hybrid of the two covers both.

Worked example and practice 6 min

Worked example: a memory design for the band saw question

Problem: Jo returns after two weeks and asks, "Can I use the band saw, and how do I change the blade?" Decide what is kept where.

  1. List the facts needed. Jo's training status on the band saw; the blade-change steps; the system rules. Reason: you must know each fact's source before you pick its place.
  2. Training status is a record that must be right. The program reads it from the staff database and puts "Jo: band saw trained, valid" in the context before the first call. Reason: it must survive between sessions and must not rely on the model's note.
  3. The blade steps are in a long manual. Use retrieval: the model calls search_manuals("band saw blade change"). Only the top chunk (say, 400 tokens) comes back. Reason: the manual is too long to load every time.
  4. The system prompt and tools stay fixed in every call. Keep them short. Reason: they are paid for at every step.
  5. At the end, save one short note if something new was learned, such as "Jo prefers evening slots." Reason: this is the only way a later session can know it.
Your turn

Lee asks: "Is the vinyl cutter free Tuesday? Last time I said I only come after 4 pm. Also, what does the blinking red light mean?" Decide where each of these three things comes from: (a) the vinyl cutter's Tuesday bookings, (b) Lee's after-4-pm preference, (c) the meaning of the red light. Step 1 is given: (a) comes from a tool call to the calendar, because bookings change often. Do (b) and (c).

Show a solution

(b) The preference was stated in an earlier session, so the model cannot know it from the chat. It must come from stored notes: the program loads Lee's notes before the first call. (c) The red-light meaning is in the vinyl cutter manual. Use retrieval: search with a keyword such as "blinking red light", because it may be an exact phrase in the manual, and add the best chunk to the context. Then the model combines all three: free slots after 4 pm on Tuesday, and the light's meaning, with the manual page as the source.

Summary 2 min

  • The model sees only the context of the current call. Everything in it counts toward the window and the cost.
  • Nothing is kept between calls. The program re-sends the whole history, so each step costs more than the one before. Trim it with short tool results, clearing and compaction.
  • Nothing is kept between sessions unless the program saves it. Notes and records in storage are the memory; load only what is needed.
  • Retrieval finds the right chunk in a long manual: embeddings for meaning, keywords for exact strings. Small knowledge bases may not need it.
