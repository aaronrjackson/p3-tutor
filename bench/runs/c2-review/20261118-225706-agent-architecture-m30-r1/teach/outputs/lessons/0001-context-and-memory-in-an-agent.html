Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a manual that the assistant searches.

Objective O3: context window, what is kept, retrieval and notes About 30 minutes Builds on: the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals. It must also remember each student's training status between visits. And your sponsor pays for every token. These three needs all depend on one question: what does the model see, and when? This lesson gives you the answer to defend at your design review.

Warm-up 2 min

Recall

From memory: in the agent loop, the model asks for a tool. Who runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool. It then sends the result back to the model, and the model is called again. Each pass round the loop is a new model call. Today's question is: what does the model see in each of those calls?

The context window 5 min

Why it matters. You cannot design the assistant until you know what the model can see. If the model cannot see a fact, it cannot use it.

The context is all the text the model reads in one call. It holds the system prompt (the standing rules), the tool descriptions, the conversation so far, and any tool results. The model writes its answer from this text and from what it learned in training. It cannot see any other facts about your makerspace.

The context window is the maximum size of the context. It is counted in tokens. A token is a small piece of text, often part of a word. The window includes the text the model reads and the text it writes (Claude documentation: context windows).

The model has no memory of its own between calls. Each call starts from the text that the program sends. The model does not "remember" the last call. The program sends the earlier text again.

An analogy, with limits. Think of a tutor who has a bad memory. Before each meeting, an assistant gives the tutor a printed folder. The tutor reads the folder, answers, and forgets everything when the meeting ends. Here is how the parts match:

In the analogyIn the agent
The printed folderThe context
A limit of 100 pagesThe context window
One meetingOne model call
The assistant who prints the folderThe program around the model

The analogy stops in one place. A real tutor reads for free. A model charges for every token it reads, on every call. A 100-page folder costs 100 pages each time.

Example: one question to the makerspace assistant

A student asks, "Is the laser cutter free on Friday?" The first call sends this context:

  1. System prompt: "You help students at the makerspace. Be short." (about 15 tokens)
  2. Tool descriptions: check_calendar, search_manuals (about 200 tokens)
  3. The student's question (about 10 tokens)

The model reads about 225 tokens and asks for check_calendar. These numbers are made up to show the shape. Real counts depend on the model and the text.

Nuances.

  • Nuance 1: the window is shared. Input and output both count. A long answer leaves less room for input.
  • Nuance 2: more text does not mean better use of it. Anthropic's engineers describe "context rot": as the number of tokens grows, the model recalls details from the context less well (Anthropic, Effective context engineering for AI agents). A bigger window is a bigger limit. It is not a promise that the model uses every token well.
  • Nuance 3: the tool descriptions use space too. Ten tools with long descriptions cost tokens on every call.
A common mix-up

"The model remembers what I told it earlier." It does not. It is tempting because chat apps feel continuous. But the app is sending the old messages again with each new one. If the program leaves a message out, the model has never seen it.

Check yourself

A student told the assistant, in call 1, that they use a wheelchair. In call 2, the program sends only the new question. What does the model know in call 2?

Show the answer

The third option. The model sees only the text in the current call. The program must send the earlier text again, or the fact is gone.

What is kept between steps 5 min

Why it matters. An agent makes many calls for one request. The cost of the request depends on what each call carries.

Inside one request, the program keeps a list of messages. After each step it adds the model's tool request and the tool's result to the list. Then it sends the whole list again. So the context grows at every step. We call this list the history of the request.

Example: the cost of "Is the laser cutter free tomorrow at 3 pm, and do I need training?"

Use made-up token counts. The start of the context is 225 tokens. Each tool result adds 300 tokens. The model writes about 50 tokens per call.

  1. Call 1 reads 225 tokens.
  2. Call 2 reads 225 + 50 + 300 = 575 tokens.
  3. Call 3 reads 575 + 50 + 300 = 925 tokens.
  4. Call 4 reads 925 + 50 + 300 = 1,275 tokens, and writes the final answer.

The total read is 225 + 575 + 925 + 1,275 = 3,000 tokens. The final context holds only 1,275. The request paid for the early text four times. Most providers charge per token, so a long request costs much more than the size of its final context, because early text is paid for again at every call. Prompt caching (the provider stores text it has already read and charges less when you send the same start again) can lower the price of text that repeats at the start of each call. Check your provider's price page.

Nuances.

  • Nuance 1: big tool results are expensive. A manual page of 3,000 tokens is read again at every later call. Keep tool results short.
  • Nuance 2: old results can be dropped. If the model no longer needs a result, the program can remove it or replace it with a short note. Anthropic's context management feature clears old tool results this way, while keeping a record that the call happened (Anthropic, Managing context).
  • Nuance 3: long histories can be summarized. When a request gets very long, the program can ask the model to write a short summary, then start a fresh context with the summary.
  • Nuance 4: the step limit protects the budget. You met the step limit in the agent loop. It also caps the growth shown in Figure 1.
A common mix-up

"A bigger window fixes everything." It is tempting because it removes the hard limit. But a bigger window does not cut cost, since you pay per token read. It also does not stop context rot. The window is a ceiling. What you put under it is still your design choice.

Check yourself

A request makes 5 calls. Every tool result is 500 tokens. The start of the context is 200 tokens. Ignore the model's own output. How many tokens does call 5 read?

Show the answer

2,200 tokens. Call 5 comes after four tool results, because the fifth tool result does not exist until after call 5 is made. Add the start (200) and four results (2,000).

What is kept between sessions 5 min

Why it matters. A student trains on the laser cutter on Monday. On Thursday they come back and ask to book it. The assistant must know about Monday.

A session is one conversation or request, from its first message to its end. When the session ends, the context is gone. The model keeps nothing. Nothing is saved unless your program saves it.

Memory, in an agent, is information that your program stores outside the context and brings back into a later context. The model does not do this by itself. You design it: what to store, where, and when to read it back.

So there are two kinds of storage, and they work differently:

ContextSaved memory
LifetimeOne call, or one requestUntil you delete it
Size limitThe context windowYour disk or database
CostPaid in tokens at every callPaid in tokens only when you read it into the context (plus the small cost of storing it and, for retrieval, building the index)
Who sees itThe model, alwaysThe model, only if the program loads it
Example: Monday's training reaches Thursday's booking
  1. Monday: the student finishes laser-cutter training. A staff member (or a tool) writes a row to a database: {"student": "s1042", "machine": "laser", "trained": "2026-11-16"}.
  2. Thursday: a new session starts. The context is empty except for the rules and the question.
  3. The model asks for check_training_record("s1042", "laser"). The program reads the database and returns the row.
  4. The row is now in the context. The model can answer, "Yes, you finished training on 16 November. Booking now."

The model never "remembered" Monday. The database did. The tool brought the row into the context.

Nuances.

  • Nuance 1: facts like training status belong in a database, not in the model's text. A database row is exact. A paragraph of chat history is not, and it costs tokens on every call.
  • Nuance 2: you choose what to store. A whole transcript of each session is costly to reload. A few exact facts are cheap.
  • Nuance 3: stored data can go stale. If a student's training expires, the old row is now wrong. Store dates, and let the tool check them.
  • Nuance 4: privacy. Store only what the assistant needs. Training status is needed. A student's personal chat is not.
A common mix-up

"The assistant remembers earlier visits automatically." It is tempting because people do. But a model call has no store between sessions. If you want memory, you must build it. Without it, every visit starts blank.

Check yourself

Where should the assistant keep "student s2210 passed 3D-printer training on 2 March"?

Show the answer

The first option: a database with a lookup tool. It lasts between sessions, it is exact, and it only costs tokens when the model asks for it.

Retrieval: finding the right page 6 min

Why it matters. The makerspace manuals are long. One laser-cutter manual can run to hundreds of pages. If you put every manual in every context, you pay for all of it on every call. It may also not fit, and the model may use it badly (context rot, from earlier).

Retrieval means that the program searches the manuals, finds the few passages that match the question, and puts only those passages into the context. The model reads a few pages instead of a library.

A common method, often called RAG (retrieval-augmented generation), has these steps:

  1. Before any question: split each manual into chunks, short passages of a few paragraphs.
  2. Build a search index over the chunks. A keyword index finds exact words. An embedding index turns each chunk into a list of numbers that captures its meaning, so that chunks with similar meaning are found even when the words differ.
  3. When a question comes: search the index and take the best few chunks.
  4. Put those chunks in the context, and let the model answer from them.
Example: "What speed do I use to cut 3 mm acrylic on the laser cutter?"
  1. The question goes to search_manuals("laser cutter acrylic 3 mm speed").
  2. The index returns three chunks. The best one is a table titled "Material settings", with a row for acrylic.
  3. The program puts the three chunks (about 900 tokens) in the context.
  4. The model reads the row and answers, with the page number from the chunk.

The model read 900 tokens, not 400 pages. In an agent, retrieval is usually a tool: the model asks for it, and the program runs it, as in the agent loop. In simple RAG, the program can run the search before the first model call.

Nuances.

  • Nuance 1: a chunk can lose its meaning. A chunk that says "The setting is 40%" does not say which machine or material. Anthropic's Contextual Retrieval adds a short note to each chunk before indexing, such as "From the laser cutter manual, material settings". In Anthropic's tests this cut failed retrievals from 5.7% to 2.9% when combined with keyword search (Anthropic, Contextual Retrieval).
  • Nuance 2: keyword and meaning search catch different things. Exact words like a part number, "M3 bolt", suit keyword search. A question like "why does my cut look burnt?" suits embeddings. Using both is common.
  • Nuance 3: retrieval can miss. If the right chunk is not found, the model cannot see it. It may then answer from its training and sound sure. Tell the model in the system prompt to say "I did not find this in the manuals" when the chunks do not answer the question.
  • Nuance 4: chunk size is a trade-off. Small chunks are cheap and exact, but lose surroundings. Large chunks keep surroundings, but cost more tokens.
  • Nuance 5: the agent can search more than once. If the first search is poor, the model can change the words and search again. Anthropic calls loading information when needed, instead of all up front, "just in time" retrieval (Anthropic, Effective context engineering).
A common mix-up

"Retrieval means the model reads the whole manual and finds the page." It does not. The model only reads what the search puts in its context. The search step decides what the model can see. A bad search gives a bad answer, even with a good model.

Check yourself

The manual says "Set power to 60% for oak." The assistant is asked about oak and answers, "I could not find that." Where is the most likely fault?

Show the answer

The third option. A good first step is to print what the search returned. If the oak chunk is missing, fix the chunking or the search words.

Notes as memory 4 min

Why it matters. Some tasks are long, and the context fills up. Some facts are learned during the task, and no database has them. The agent needs a place to write things down.

Notes are text that the agent writes to storage outside the context, to read back later. Anthropic describes this as "structured note-taking": the agent writes notes to memory outside the context window, and reads them back in later turns (Anthropic, Effective context engineering). Anthropic's memory tool works this way. It lets the model store knowledge in a file system. Your own program runs the file operations on storage you control (Anthropic, Managing context).

Notes are different from retrieval. Retrieval reads documents that people wrote. Notes are written by the agent for its own future use.

Example: a note that helps next week
  1. A student asks for the laser cutter on Friday. Friday is full. The student says, "Mornings only, I have class after 1 pm."
  2. The assistant books Saturday morning. It then writes a note to the student's file: prefers mornings; no bookings after 13:00.
  3. Next week, a new session starts. The program loads the student's note file into the context at the start (about 20 tokens).
  4. The student asks for a slot. The assistant offers only mornings, with no repeated questions.

Nuances.

  • Nuance 1: the model decides what to write, so notes can be wrong. A note that says "student is trained" without a source is a risk. For facts that matter, such as safety training, use the official record, not a note.
  • Nuance 2: keep notes short and loaded early. Notes that grow without limit become a second context problem.
  • Nuance 3: someone must check notes for privacy. A note file holds personal information. Decide who can read it and when it is deleted.
A common mix-up

"Notes and the context are the same thing." They are not. A note is in storage. It is in the context only when the program loads it. Writing a note does not remove anything from the current context.

Check yourself

Which fact is best kept as an agent-written note, not as a database record or a manual chunk?

Show the answer

The third option. A preference learned in chat has no other home, and a mistake is cheap. Safety training and machine settings both have a better, official source.

Summary 2 min

  • The context is all the text a model reads in one call. The window limits its size, and you pay for every token read.
  • Inside one request, the program re-sends a growing history at each step. Keep tool results short and drop old ones.
  • Nothing lasts between sessions unless your program saves it. Exact facts go in a database that a tool reads.
  • Retrieval puts only the matching chunks of a long manual in the context. A bad search means a blind model.
  • Notes are text the agent writes for its later self. Use them for low-risk facts that no other source holds.

Say it in your own words: a student returns after a week and asks how to cut acrylic. Without looking, say what is in the context for the first call, and where each fact the assistant needs comes from.
