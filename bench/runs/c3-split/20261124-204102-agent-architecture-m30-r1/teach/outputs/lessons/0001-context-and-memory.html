Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what stays in context, what is saved between sessions as notes, and how the assistant finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your sponsor gave you a small model budget. The machine manuals are long. Students come back each week and expect the assistant to know their training status. Three decisions control the cost and the quality of the assistant: what it holds in context, what it saves, and how it finds a manual page. This lesson gives you a way to make each one.

Warm-up 2 min

Everything in this lesson comes down to one fact from your earlier work: the model knows only what it learned in training, plus the text it is given. Memory, tools and retrieval are all ways to decide which text it is given. Try two questions first. Answer each one in your head, then check.

Recall 1

Why can a chatbot state an outdated fact with confidence?

Check your answer

Its knowledge stops where its training data stops. It writes plausible text, whether the text is true or not. Today you will see how to give it newer facts at run time: as text in its input.

Recall 2

In the agent loop, which part runs a tool? What happens to the result?

Check your answer

The program runs the tool, not the model. The result goes back to the model as new text, and the model is called again. Each of those calls is a separate model call, and that fact matters in Section 2. (The memory tool documentation describes the same loop: the model asks, and your application runs it.)

The context window and tokens 5 min

A model reads text in small pieces. A token is one such piece: a word, part of a word, or a single character (Claude glossary). As a rough rule, one token is about 3 to 4 characters of English text. The exact size changes from model to model.

The context window is all the text the model can use when it writes one response. It includes the response itself (Context windows). The window has a fixed size, counted in tokens. Tokens also set your bill: you pay for the tokens you send and the tokens the model writes.

Here is an everyday picture. A meeting room has one whiteboard with 40 lines. The board is the context window. One line is about one token. The speaker reads the whole board before each reply, and the reply also needs lines on the board. The picture stops working in one place: a board costs nothing per line, but tokens cost money. The picture also stops working because the model does not look at lines as a person does.

Example: one call about the band saw

A student asks: "How do I change the blade on the band saw?" The assistant makes one model call. These numbers are round, for illustration only.

  1. Instructions for the assistant: about 300 tokens.
  2. Descriptions of the tools: about 400 tokens.
  3. The student's question: about 20 tokens.
  4. The manual page that answers it: about 700 tokens.
  5. The model's reply: about 200 tokens.

Total: about 1,620 tokens. All five parts share one window. The docs say it plainly: the system prompt (the rules), every message, the tool results and the tool definitions all count toward the window, and so does the output (Context windows).

Nuances

  • Nuance 1: A token is not a word. A rare or long word can take several tokens. The size of a token also depends on the model: newer models can use more tokens for the same text (Claude glossary).
  • Nuance 2: The window holds the input and the reply together. If the input alone is too long, the API refuses the request. If the reply reaches the limit, the model stops writing (Context windows).
  • Nuance 3: Every token you send is a token you pay for. A short context costs less. This is the link to the sponsor's budget.
Check yourself

The assistant sends a call with its rules, a manual page and a question. What does the context window limit?

Show the answer

The second option is right. The window is a limit on the total tokens in one call, counting the reply. The other options name things that do not set that limit.

Each step sends everything again 5 min

Think back to the agent loop. Each step is a separate model call. A call keeps nothing from the call before. We call this stateless: the model holds no state between calls, and the program supplies all of it. In the Claude API, each request must carry the full history. Each new input holds all earlier messages plus the new one (Context windows).

An everyday picture: a helper has total amnesia. Before each reply, you hand the helper the full printed transcript of the talk so far. The helper is the model. The transcript is the history the program sends. Handing it over is one model call. The picture stops in one place: a person would tire of re-reading, but the model has no such limit. It has only the window and your bill.

Example: "Is the laser cutter free on Friday, and book me for 2 pm"

The assistant needs three model calls. The numbers are round and for illustration.

  1. Call 1 sends the rules, the tool descriptions and the question: about 400 tokens. The model asks for check_calendar.
  2. Call 2 sends all of call 1, plus the tool request and the calendar result: about 900 tokens. The model asks for book_slot.
  3. Call 3 sends all of call 2, plus the booking request and its result: about 1,300 tokens. The model writes the final answer.

Tokens sent in total: 400 + 900 + 1,300 = 2,600. The final context holds only 1,300 tokens, but you paid for 2,600.

Nuances

  • Nuance 1: The program keeps the history. The model does not. This follows from what you learned before: the program runs each tool, and each step is a separate model call.
  • Nuance 2: A long tool result stays in the history. A 5,000-token manual page sent at step 2 is sent again at step 3, 4 and 5. It costs you at every step.
  • Nuance 3: You can keep the history small. Clear old tool results. Summarize earlier steps. Anthropic calls the summary step compaction, and calls clearing old tool results one of the safest light forms of it. It warns that cutting too hard can lose small but important facts (Effective context engineering). A step limit in your program also stops a loop that grows without end. That one is design advice from this lesson, not from the source.
Check yourself

An assistant request takes four model calls. What is true about the input of call 4?

Show the answer

The last option is right. The program sends the full history at every call, so call 4 is the longest. The other options suppose that the model keeps something by itself, or that the input stays the same size.

Between sessions, notes are memory 5 min

A session is one conversation, from start to end. When it ends, the context is gone. The next session starts with an empty window. The assistant can know something from last week only if the program saved it and loads it again.

That saved information is memory: facts kept outside the context and loaded back in. A simple form is a note, a small saved record. Anthropic describes the same idea: the agent regularly writes notes that persist outside the context window, and reads them later (Effective context engineering). The Claude memory tool is a second way: the model itself asks to read and write memory files, and your code carries out each request. Memory lives in your application (Memory tool).

An everyday picture: a shop whiteboard that someone wipes each night, and a paper folder for each student in a cabinet. The whiteboard is the context. The wipe is the end of the session. The folder is the notes file. Taking out the folder in the morning is the program loading the notes. The picture stops in one place: in Dana's example below, the program opens the folder for the model. The model reads only what the program puts in the context.

Example: Dana's training status

Dana finished laser cutter training on Monday. On Thursday she opens a new chat and asks to book the laser cutter.

  1. Without saved notes: the window is empty. The assistant cannot know that Dana was trained.
  2. With a saved note: the program reads Dana's record at the start of the session.
  3. The program writes one line into the context. The model now sees it.
import json

notes = json.load(open("notes/dana.json"))
# {"student": "dana", "trained": ["laser cutter"], "date": "Mon"}

line = f"Student {notes['student']} trained on: " + ", ".join(notes["trained"])
messages = [{"role": "user", "content": line + "\n" + question}]

The model never opened a file. The program did that, and put one short line in the input.

Nuances

  • Nuance 1: Save facts that last, such as training status. Do not save the whole chat. Loaded text costs tokens at every call of every later session. The memory tool docs also suggest limits on file size and the removal of old files (Memory tool).
  • Nuance 2: A note can be old or wrong. Store the date with it, and let a staff member correct a record. (This is design advice from this lesson.)
  • Nuance 3: Training status decides who may use a machine. Keep it in the program's own database, and have the program check it. The model may read it, but the model must not be the only guard. This is also a design choice, not a rule from a source.
Check yourself

On Thursday the assistant must know that Dana was trained on Monday. What makes that possible?

Show the answer

The first option is right. Between sessions only what the program saved can return. The other options suppose that the model or the window keeps things by itself.

Retrieval finds the right page 5 min

Some manuals are too long for the window. Even a manual that fits costs tokens at every step. The fix is retrieval: search the manual, and put only the best few pieces into the context. Anthropic says that for knowledge bases that do not fit in the window, this approach (RAG, retrieval-augmented generation) is the typical solution (Contextual Retrieval).

Three terms. A chunk is a small piece of a document, such as one section. An index is a prepared list that makes searching fast. The search returns the top few chunks, and the program passes them to the model as context.

There are two ways to search. Search by keywords matches exact words, and works well for names and part numbers. Search by meaning uses embeddings. An embedding is a list of numbers that stands for the meaning of a text, so texts with similar meaning get similar numbers. It matches ideas, so "change the blade" can match "replace the saw band". Embeddings can miss exact matches, and keyword search is good at them (Contextual Retrieval). Many systems use both. You do not need the math for this.

An everyday picture: the index at the back of a book. An index entry is an entry in the search index. The page number is a chunk. Reading only the pages the index names is putting only the best chunks in context. The picture stops in one place: a book index matches exact words, and a search by meaning can match different words.

Example: the band saw manual

The band saw manual has 120 pages, about 60,000 tokens. A student asks: "How do I change the blade?"

  1. Before any question: split the manual into 240 chunks of about 250 tokens. Tag each chunk with the machine and the section.
  2. The student asks the question.
  3. The search returns the top 3 chunks: about 750 tokens.
  4. Only those 3 chunks go into the context.

The call now carries 750 tokens of manual, not 60,000. That saving repeats at every step of the request, because of what you learned in Section 2.

Nuances

  • Nuance 1: Retrieval can return the wrong chunk, and then the answer can be wrong. The quality of RAG depends on the quality of what is retrieved (Claude glossary). Test it with real student questions.
  • Nuance 2: A chunk can lose its meaning when it is cut out. "Remove the guard" does not say which machine. Anthropic adds a short explanation of context to each chunk before indexing it, which fixes this (Contextual Retrieval). Your machine and section tags are a simple form of the same idea.
  • Nuance 3: Retrieval can be a tool. Then the model decides when to search and with which words (Claude glossary). That is the agent loop from your earlier work.

Deciding what goes where 3 min

Each piece of information has one best place: in the context now, in saved notes, or in a searchable store. Ask three questions about it.

  1. Does the model need it at every step?
  2. Does it last past this session?
  3. Is it too long to carry in the window?
InformationEvery step?Past the session?Too long?Place
The assistant's rulesYesYes, but shortNoIn context, every step
This question and this request's tool resultsFor this requestNoNoIn context, trimmed after use
Training statusThis requestYesNoSaved notes, loaded at session start
Machine manualsNoYesYesSearchable store, best chunks only

Nuances

  • Nuance 1: Information can move. A retrieved chunk stays in the history until the program trims it or the session ends.
  • Nuance 2: Every item in the context costs tokens at every step. Ask what can leave. Anthropic's aim is the smallest set of high-signal tokens that gives the result you want (Effective context engineering).
  • Nuance 3: The booking calendar changes all the time, so a saved copy goes stale. The assistant reads it with a tool when it needs it. Anthropic describes this as loading data at run time with tools (Effective context engineering).
Check yourself

The makerspace changes its opening hours each term. The assistant must tell students the hours. Where should the hours go?

Show the answer

The second option is right. Apply the three questions: the hours are short, shared by all students, and change only once a term. Short text in the rules, or one small stored page, is easy to update once. A live tool would suit data that changes by the minute, like the calendar.

Four mix-ups 2 min

Mix-up 1: the model remembers old chats by itself

It looks true because a chat app seems to remember you. But the model keeps nothing between calls. If an app seems to remember, its program saved the text and sends it again. Dana's Thursday session shows it: with no saved note, the assistant knows nothing about Monday.

Mix-up 2: a bigger window means I can send everything

It looks true because the manual might fit. But each step sends the history again, so the cost grows at every step. And more text is not always better: as the token count grows, the model's ability to recall information from the context decreases (Effective context engineering).

Mix-up 3: inside one request, the model remembers earlier steps

It looks true because the answer at step 3 uses step 1. But the program sent step 1 again. Remove it from the history, and the model loses it.

Mix-up 4: a token is a word

It looks true because the sizes are close. But a token can be part of a word or one character. Use tokens, not words, when you plan cost.

Worked example and practice 6 min

Worked example: Dana asks about acrylic

Dana, trained on the laser cutter, writes: "Can I cut 6 mm acrylic, and what are the power settings?" Follow one request from start to end. At each step, use the three questions.

  1. Load notes. The program reads Dana's record: trained on the laser cutter. Needed at every step of this request? Yes, because the booking depends on it. Lasts past the session? Yes, so it is a saved note. The program puts one line, about 40 tokens, in the context.
  2. Retrieve. The manual is long, so it is in the searchable store. The search runs on "acrylic 6 mm power". It returns the top 3 chunks of the laser cutter manual, about 750 tokens.
  3. Build the context. Rules, about 300. Tool descriptions, about 400. Notes line, about 40. Question, about 30. Three chunks, about 750. Total: about 1,520 tokens.
  4. Answer. The model reads all of it and writes the answer. If Dana asks to book, it requests the booking tool. The calendar is read live. Nothing about the calendar is saved.
  5. After the session. The program trims the three chunks, or they leave when the session ends. Save a new fact only if it will last, for example "asked about acrylic". Everything else is gone with the context.

  2. Retrieve. What words would you search for, and in which manual?
  3. Build the context. List every part that goes in.
  4. Answer. Which question needs saved notes, and which needs the manual?

Show a solution

2. Search the 3D printer manual for "filament type" with the printer's name. 3. The rules, the tool descriptions, the notes line, Marco's question, and the top 3 chunks about filament. 4. "Am I cleared" is answered from the saved note. "What filament" is answered from the retrieved chunks. The program, not only the model, must check clearance before anyone books the printer. 5. Summary 2 min

  • The context window limits what the model reads in one call, counted in tokens. Tokens are also the cost.
  • Each step sends the history again. The model keeps nothing between calls, so the cost grows at every step.
  • Between sessions only saved notes remain. The program saves them and loads them.
  • Retrieval puts only the best chunks of a long manual in the context. Three questions place each piece of information.
